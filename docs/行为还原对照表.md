# 行为还原对照表

> 本表逐条列出原版 Windows 游戏 **mine2000**（1999–2005, Kazuhiro Toyama / AhoSoft）
> 的可观测行为，以及本 macOS 移植版（Swift 6 + AppKit）的实现状态。
>
> **标注约定**
>
> | 标记 | 含义 |
> |---|---|
> | ✅ | **已实现**，且有反汇编 / 像素级 / 二进制级证据 |
> | ⏳ | **部分实现**，或实现方式与原版存在差异（已在备注中写明） |
> | ❌ | **未实现** |
> | [已确证] | 结论来自对 `mine2000.EXE` 的字节级验证（给出 VA） |
> | [推断] | 结论来自行为合理性与图集/美术资源反推，**未逐字节确证** |
>
> 证据文件：`docs/research/本轮反汇编结论.md`（本轮实测汇总）。

## 2. 棋盘与游戏规则

| 行为 | 状态 | 实现 / 证据 |
|---|---|---|
| 左键翻开格子 | ✅ | `BoardView.mouseUp` → `Board.reveal` |
| 右键插旗 / 再右键取消 | ✅ | `BoardView.rightMouseUp` → `Board.toggleFlag` |
| 中键 chording（扫雷） | ✅ | `BoardView.otherMouseDown`（`buttonNumber == 2`）→ `Board.chord` |
| 左右键同按 chording | ✅ | `BoardView.rightMouseDown` 检测 `pressedCell != nil` → `bothButtonsPressed` |
| 首点必安全（不落雷） | ✅ | `Board.placeMines(excludingRow:excludingColumn:)`；反汇编 `0x401844` 比较首点坐标后跳过 |
| 首点后才布雷 | ✅ | `Board.minesPlaced`；反汇编 `0x401890` 只清棋盘，布雷在点击时 |
| 布雷算法（`rand()%列/行`，占用则重试） | ✅ | `Board.placeMines`；反汇编 `0x401800` 附近 |
| 3×3 邻域雷数统计 | ✅ | `Board.computeAdjacentMineCounts`；反汇编 `0x401E3A` 起双层循环 |
| 空白区连锁展开（flood fill） | ⏳ | `Board.expandFrom` 用显式栈实现。**触发条件与原版是否完全一致未逐字节确证**，按标准扫雷实现 → [推断] |
| chording 触发条件（旗数 == 邻雷数） | ⏳ | `Board.chord` 按标准扫雷规则实现。原版**确实存在**该操作（`SetCapture`/`ReleaseCapture` 导入 + `0x401E07` 附近 3×3 邻域遍历），但「旗数 == 雷数」这一具体条件未确证 → [推断] |
| 胜负判定（全部非雷格翻开 = 胜） | ✅ | `Board.checkWin`；反汇编 `0x4029DF`：`cmp eax,[0xC194]`（雷数字段） |
| 结束态锁定（结束后棋盘不变） | ✅ | `Board.reveal` / `Board.toggleFlag` 开头 `if state.isFinished { return }` |
| 失败时揭示全部地雷 | ✅ | `BoardView.draw` 中 `state == .lost` 分支；图集 A1c2 = 地雷 |
| 失败时标出刚踩中的那颗（红底） | ✅ | `Board.hitMinePosition` / `isHitMine`；图集 A1c3 =「地雷 + 红底高亮」 |
| 失败时给插错旗的格子画 X | ✅ | `Board.wrongFlagPositions` / `isWrongFlag`；图集 A1c4 =「地雷 + 红色 X」 |
| 胜利后自动给所有雷插旗 | ⏳ | `Board.autoFlagAllMines`；经典扫雷行为，原版对应 `0x4029F0` 调用胜利处理函数 → [推断] |

## 3. 计时与计分

| 行为 | 状态 | 实现 / 证据 |
|---|---|---|
| 用 `timeGetTime` 计时（毫秒精度） | ✅ | `GameSession` 用 `Date` 差值；原版导入 `WINMM.timeGetTime`（`0x40852C`） |
| 计时基准 = **关卡初始化时刻**（非首次点击） | ✅ | `GameSession.baselineDate` 在 `init`/`restart` 时设定；反汇编 `0x401ECC`（重置）与 `0x402894`（难度初始化）均调用 `timeGetTime()` 存入 `+0xC1A4` |
| 未开始时显示 0 | ✅ | `GameSession.elapsedDeciseconds` 在 `state == .ready` 返回 0；反汇编 `0x401C6C`：`xor eax,eax; ret` |
| 结束后用时冻结 | ✅ | `GameSession.freezeTimerIfFinished`；反汇编 `0x40252D`/`0x402940` 写 `+0xC1A0`，之后计时函数走 `0x401C64` 返回冻结值 |
| 计分单位 = **0.1 秒（十分之一秒）** | ✅ | `HighScoreEntry.deciseconds(from:)`；反汇编 `0x401C46`：`(Δms * 0x51EB851F) >> 37` ≡ `Δms / 100`，即 1 单位 = 100ms；1000ms → 10 单位 |
| 成绩显示格式 `%d.%d秒` | ✅ | `ScoreFormat.format(deciseconds:)`；`.rdata` `0x408F60` = CP932 `"%d.%d秒"`（字节 `25 64 2e 25 64 95 62 00`） |
| 成绩排名：用时**越小越好** | ✅ | `HighScoreTable.submit`；反汇编 `0x402539`：`cmp edx,eax; jle`（仅当新成绩严格更小才插入） |
| 同分时先达成者在前 | ✅ | `submit` 用严格 `<` 比较，新记录插在同分记录之后 |
| 入榜提示语 `%d位にランクイン！！` | ✅ | 格式串已在 `.rdata` `0x408F68` 定位，已用作输入框标题 |

> **与早前报告的差异（重要）**：早前实现把计分单位当成「百分之一秒」并输出 `"%d.%02d"`（无「秒」后缀），
> 与反汇编不符，已按字节证据修正为「0.1 秒 + `%d.%d秒`」。
> 验证：Δ = 1000ms → 单位值 10 → 显示 `"1.0秒"` ✓ 自洽。

原版表情由 **游戏状态 × 鼠标状态** 共同决定，共 5 张脸。

| 条件 | 状态 | 槽位 | 证据 |
|---|---|---|---|
| 未开始 / 游戏中，鼠标未按下 | ✅ | 槽 0 正常微笑 | `FaceExpression.expression(for:)`；反汇编 `0x403A1C` 跳转表 state1/state2 **共用分支 `0x40388E`**，其中 `[0x90]==ebx` 时取源 x = `0x00` |
| 未开始 / 游戏中，鼠标在棋盘上按下 | ✅ | 槽 3 惊讶（O 形嘴） | `FaceState.surprised`；反汇编 `0x4038FA` 取源 x = `0x4E` |
| 鼠标不在棋盘范围内 | ⏳ | 槽 4 备用脸 | 图集有该图块（`FaceExpression.idle`），但**鼠标离开棋盘时的切换未接入 UI**（`BoardView.mouseExited` 已有回调，未接表情）→ [推断] |
| 胜利 | ✅ | 槽 1 墨镜 | `FaceExpression.win`；反汇编 `0x403974` 取源 x = `0x1A`（状态 3 分支 `0x40391F`） |
| 失败 | ✅ | 槽 2 X 眼 | `FaceExpression.lose`；反汇编 `0x4039A2` 取源 x = `0x34`（状态 4 分支 `0x403978`） |

### 7.1 难度译名的依据（从「难度」而非「词源」出发）

| 原版 | 尺寸 | 雷数 | 密度 | = Windows 扫雷 | 官方中文名 | 本移植用名 |
|---|---|---|---|---|---|---|
| 初級 | 8×8 | 10 | 15.62% | Beginner | 初级 | **初级** |
| 中級 | **16×16** | **40** | 15.62% | Intermediate | 中级 | **中级** |
| 上級 | **30×16** | **99** | 20.62% | Expert | **专家** | **专家** |
| 超上級 | 48×24 | 256 | 22.22% | 超出 | — | **大师** |
| マニア | 64×48 | 777 | **25.29%** | 远超 | — | **宗师** |

- **中級 / 上級 与 Windows 扫雷逐字节相同** → 中文玩家的难度认知锚点就是 Windows，
  而 Windows 里 30×16/99 官方叫**「专家」**（不叫「高级」）。
- 整体构成「入门 → 进阶 → 专业 → 精通 → 登峰」的标准中文难度阶梯。
- 宗师档密度是 Windows 专家级（16.6%）的 **1.5 倍**，面积 48 倍、雷数 78 倍。
- ⚠️ 早前把「上級」直译为「高级」是**按字面译**而非**按难度认知译**，已更正。

## 9.5 本轮（2026-10-21 夜）新增确证与修复

### 9.5.1 flood fill 展开邻域 = **8 邻（3×3）**，非 4 邻 —— 更正早前误读

| 项 | 内容 |
|---|---|
| 证据 | 反汇编 `0x4028B0`（expand 函数）：<br>`0x402967 lea eax,[edi+1]` / `0x40296a lea ebx,[edi-1]` → x 遍历 3 值<br>`0x402975 lea edx,[ebp-1]` / `0x40297c inc ebp` → y 遍历 3 值<br>`0x402988–0x402994` 内层 `call 0x4028b0`（递归）<br>`0x40299a inc ebx` / `0x40299d jle 0x402980` → 外层 |
| 结论 | x、y 各 3 个值 → **3×3 = 8 邻域（含 4 个对角）**，与经典扫雷一致 |
| 更正 | 《20261021_原版内部结构_反汇编确证》原写「展开四邻」，是误读，已在该文档中标注更正 |
| 本实现 | `Board.expandFrom` 用 `dr in -1...1 / dc in -1...1`，**与之一致，无需改动** |
| 展开条件 | 该格周围雷数 == 0（`0x402914 test eax,eax` / `je 0x402951`） |

### 9.5.2 AppKit 会**静默丢弃没有 submenu 的顶级菜单项**（macOS 平台特有）

这是本轮最花时间、也最有价值的发现。

| 项 | 内容 |
|---|---|
| 现象 | 菜单栏显示为 `Apple logo → ゲーム → ヘルプ`，**应用名完全不出现**，「ゲーム」被加粗显示在最左 |
| 根因 | macOS 菜单栏最左侧的加粗槽位**永远渲染 `mainMenu.items[0]`**。AppKit 会**静默丢弃**没有 `submenu` 的顶级项，于是「ゲーム」升为 `items[0]` 并占据了 App 菜单槽位 |
| 为什么难发现 | `NSMenu.items` 数组**看不出**丢弃（数组内容不变），单元测试断言 `titles.first == "MineSweeper 2000"` **照样通过** |
| 唯一可靠判据 | 读 AX 树：系统真实渲染的菜单栏标题序列 |

## 9.6 按压反馈：凹陷底板（本轮修复的真 bug）

### 现象

用户实测反馈：「点击格子时，按下去的瞬间会先显示一个雷」。

### 根因

按压反馈**错用了 `.mineHighlighted` 图块**（红底高亮的雷）。
该图块的正确用途是**失败态标记刚踩中的那颗雷**，与按压反馈完全无关。

### 原版规格（反汇编 `0x403c20`，字节级确证）

```
00403d79  mov eax, [ecx+0x90]    ; 鼠标按键状态
00403d7f  cmp eax, 2             ; 状态 2 = 单键按下
00403d84  cmp [ecx+0x88], edx    ; 鼠标 x == 该格 x
00403d90  cmp [ecx+0x8c], edx    ; 鼠标 y == 该格 y
00403d96  je  0x403dc9           ; → 该格画凹陷底板
00403d98  cmp eax, 3             ; 状态 3 = 左右同按
...       |鼠标 - 该格| <= 1 判定 ; 该格及八邻都凹陷
00403dc9  push 0                  ; 源 y = 0 → 区域 A 第 0 行
```

### 图块对照（像素级实测）

| 图块 | 源坐标 | 左上 1px | 语义 |
|---|---|---|---|
| `.coveredCell` | (0, 16) | **255 白高光** | 凸起（未翻开） |
| `.blankPlate` | (0, 0) | **128 暗边** | **凹陷（按压反馈）** |
| `.mineHighlighted` | (48, 16) | 红底 144 px + 黑雷 | 失败态标记刚踩中的雷 |

### 本轮改动

| 项 | 改动 |
|---|---|
| `BoardView.draw` | 按压格改用 `.blankPlate` |
| `BoardView.shouldRenderPressed` | 新增：按原版规格判定单键/双键两种凹陷范围 |
| `BoardView.mouseCell` | 新增：追踪鼠标当前所在格（原版用 `+0x88`/`+0x8C`） |
| `BoardView.mouseMoved` | 新增重写（早前缺失，导致双键凹陷范围无法判定） |
| `BoardView.simulatePressForTesting` | 新增：供单元测试注入鼠标状态 |

### 验证

| 层 | 项数 | 覆盖 |
|---|---|---|
| 单元 `PressFeedbackTests` | 8 | 判定逻辑 6 项 + **渲染级断言 1 项**（红像素=0、凹陷暗边>0、无白高光） |

## 9.8 HUD 数码管：连续槽位（用户实测反馈后的修复）

### 现象

用户实测反馈：「右上角的计时器没有像左上角一样在一个框里，割裂开了」。

### 根因（两层）

| # | 层次 | 问题 |
|---|---|---|
| 1 | 布局 | 两位秒与十分之一秒之间留了 **4px 纯空白 + 2×2 红点**，红底被拦腰截断 |
| 2 | 像素 | LED 垂直位置 `(32−23)/2 = 4.5` 是**半像素**，矩形填充被抗锯齿混合，红底发暗、与相邻槽色差 |

### 原版规格（反汇编 `0x403520` 确证）

| 项 | 值 |
|---|---|
| 贴图 | `BitBlt` 13×23、源 y=32、源 x=13×数字 |
| 目标 y | **4**（整数） |
| 目标 x | `16D−71 / −58 / −45 / −32 / −19`，**13px 连续步进、中间无空隙** |
| 槽结构 | **红底 (255,0,0) + 黑色七段字**，每槽自带红底；相邻槽之间 4px 黑边 |
| 小数点 | 图集无此图块 → **程序绘制**，独占槽位，不额外占宽度 |

### 第二轮修正（用户再次反馈「你改的还是不对」）

第一轮改法是「4 槽 + 第 3 槽为纯红空槽 + 底部黑点」，用户反馈：

> 「左边是这样是对的，右边你改的还是不对」

用户指的"左边"是**左上角雷数计数器**（3 个数字槽，红底贯通，**没有空槽**）。

**穷举确证原版没有小数点图形**：

| 证据 | 结论 |
|---|---|
| 穷举 10 个数字槽的全部 13×23 局部坐标 | **没有任何一个像素对全部 10 个数字都是纯红底**（七段字形占满槽） |
| 图集 11 个槽位 | 只有 0–9 + 空白槽（纯白），无小数点图块 |
| 反汇编 `0x403520` | 5 次 LED 贴图**全是数字图块**，**全程无绘制小数点的代码** |

→ **原版就是一排纯数字槽**，既没有空白割裂，也没有纯红空槽。

### 本移植的最终布局

> ⚠️ **本节下方「3 槽」的结论已被 §9.10 更正**：原版计时器位数按难度变
> （初级 3 位、其他 5 位）。保留此处仅为记录当时的调试过程。

```
[秒十位][秒个位][十分之一秒]
   13px     13px      13px      → 39px 连续红底（仅初级）
```

- 垂直定位：`ledTopInset = 4`（与原版 yDest 一致），底边 = 32−4−23 = **5**（整数）

### 验证

`Tests/Mine2000Tests/HUDLayoutTests.swift`（4 项）：

| 判据 | 作用 |
|---|---|
| **计时器 3 槽与图集数字图块逐像素一致** | 核心判据：一次抓住空槽 / 空白 / 混色 / 错位 |
| 雷数计数器 3 槽与图集逐像素一致 | 对照组，确保没影响左侧 |
| 计时器与雷数同为 3 槽 | 抓布局回退 |
| LED 垂直定位为整数 | 抓半像素回归 |

> ⚠️ **核心判据做了两轮 TEMP-BREAK 对照实验**：
> 注入「纯红空槽」→ FAIL；注入「4px 空白割裂」→ FAIL；恢复后全绿。
>
> 逐像素比对之所以最强，是因为它**不依赖任何"特征"假设**
> （不像"数红像素个数"那样会漏判），直接以图集为唯一真值。


## 9.9 笑脸按钮的「按下凹陷」反馈（用户实测反馈后的补实现）

## 9.10 计时器规格：单位、位数、起点（用户问「怎么跳这么快」后的彻查）

### 用户的疑问

「现在右上角的时间是怎么跳的？感觉特别快，应该不是按秒跳的吧」

### 一、单位就是**十分之一秒**（原版如此）

反汇编 `0x401C30` 计时函数：

```
00401C46  call timeGetTime            ; 当前毫秒
00401C4C  mov edx, [esi + 0xC1A4]     ; 基准
00401C54  sub ecx, edx                ; 毫秒差
00401C5B  mul 0x51EB851F / shr eax,5  ; ≈ /100 → 十分之一秒
```

状态分派：状态 1（未开始）→ 返回 0；状态 2（游戏中）→ `(now − baseline)/100`；
状态 3/4（胜负）→ 返回冻结值 `+0xC1A0`。

计分串也是 `%d.%d秒`（`.rdata 0x408F60`）。**所以最右位每 0.1 秒跳一次是设计，不是 bug。**

真机实测（每 1 秒截一张）：

| 时刻 | 显示 | 含义 |
|---|---|---|
| T1 | `508` | 50.8 秒 |
| T2 | `518` | 51.8 秒 |
| T3 | `528` | 52.8 秒 |
| T4 | `538` | 53.8 秒 |

`T4 − T1 = 3.0`，与真实间隔 3.1 秒吻合 —— **速度正确，只是刻度细**。

### 二、位数**按难度自适应**（此前实现错误）

`0x403520` 里 `cmp [列数], 8; jle` → **初级只画 3 位，其他难度画 5 位**（详见图集规格 §4.2）。

| 难度 | 计时器位数 | 旧实现 | 现实现 |
|---|---|---|---|
| 初级 8×8 | 3 | 3 ✅ | 3 ✅ |
| 中级及以上 | **5** | 3 ❌ | **5 ✅** |

**旧实现固定 3 位的后果**：`123.4 秒` 显示成 `123`，十分之一秒位被挤掉（已实测复现并修复）。

### 三、起点：改为「第一次操作」起算（**与原版的有意偏差**）

原版 `+0xC1A4`（基准）只在 5 处「关卡初始化」写，**第一次点击不重置** ——
严格说启动后发呆的时间会计入成绩。

用户 2026-10-22 拍板改为**第一次点击/插旗才起算**（`GameSession.markStartedIfNeeded`）。
这是本移植**唯一有意偏离原版**的行为，偏差仅出现在「启动后长时间不点第一格」这种非典型场景。

| 场景 | 原版 | 本移植 |
|---|---|---|
| 启动后 50 秒才点第一格 | 显示 50.0 秒 | **显示 0.0 秒** ✅ |
| 启动即点 | 0.0 秒 | 0.0 秒（一致） |

### 四、边距（顺带更正）

| 项 | 旧实现 | 原版 / 现实现 | 依据 |
|---|---|---|---|
| 雷数左边界 | 4 | **6** | `0x403B58` 的 `push 6` |
| 计时器右边界 | 4 | **6** | 末位 x = `16D−19`，+13 → `16D−6` |

### 五、验证

`HUDLayoutTests` 重写为 9 项：

| 判据 | 作用 |
|---|---|
| 位数：8 列 → 3、16/30/48/64 列 → 5 | 抓位数规则 |
| 左右边距均 6，且初级起点 83 / 中级起点 185 | 与原版 `16D−45` / `16D−71` 逐值吻合 |
