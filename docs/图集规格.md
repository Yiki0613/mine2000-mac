# 图集规格（tiles_144x81.bmp）

> 本文档的每一个结论都由 `Tools/atlas_spec.py` **独立重新切图、重新统计像素**得到，
> 不依赖任何既有分析产物（避免「用旧结论验证旧结论」）。
> 复现命令：
>
> ```bash
> cd 移植实现
> python3 Tools/atlas_spec.py
> ```

## 一、图集总览

| 项目 | 值 |
|---|---|
| 文件 | `Sources/Mine2000/Resources/tiles_144x81.bmp` |
| 尺寸 | **144 × 81 像素** |
| 格式 | 24bpp BMP，**自下而上**存储（`biHeight` 为正） |
| 用途 | 原版 EXE `.rsrc` 段中抽出的**裸 DIB**（无 `BM` 文件头） |

> **注意**：资源是从 EXE `.rsrc` 段直接抽出的裸 DIB，`NSBitmapImageRep(data:)` 无法直接读取，
> 因此项目内实现了 `View/DIBImageLoader.swift` 自行解析 `BITMAPINFOHEADER` 并按 BGR→RGBA 还原。
> 见 `View/DIBImageLoader.swift` 的类型注释。

## 二、关键结论：图集**不是** 9×5 均匀网格

早期假设「144 = 9×16、81 = 5×16，所以是 9 列 × 5 行共 45 个 16×16 图块」是**错误**的。
实际结构是 **3 个不同规格的子图集纵向拼接**：

```
y = 0  ┌─────────────────────────────────────────┐
       │ 区域 A：9 列 × 2 行 × 16×16 （格子图块）  │  高 32
y = 32 ├─────────────────────────────────────────┤
       │ 区域 B：11 个 × 13×23 （七段 LED 数字）   │  高 23
y = 55 ├─────────────────────────────────────────┤
       │ 区域 C：5 个 × 26×26 （笑脸）            │  高 26
y = 81 └─────────────────────────────────────────┘
```

**总图块数 = 9×2 + 11 + 5 = 34 个**（而非 45 个）。
「45」这一数字来自把区域 B / C 误当作 16×16 网格切分的结果。

**反汇编佐证**（与像素实测互相印证）：

| 区域 | 反汇编证据 | 说明 |
|---|---|---|
| A | `0x401E1B`: `lea eax,[edx+edx*2]; shl eax,4` | 按 **16** 步进（×3 dword/格） |
| B | `0x403660`–`0x403678`: `BitBlt` 宽 `0x0D`(13)、高 `0x17`(23)、`ySrc=0x20`(32)、`xSrc = 13*k` | 13px 步进、源 y=32 |
| C | `0x403890`–`0x403978`: `BitBlt` 宽高均 `0x1A`(26)、`ySrc=0x37`(55)、`xSrc ∈ {0x00, 0x1A, 0x34, 0x4E, 0x68}` | 26px 步进、源 y=55 |

## 三、区域 A：格子图块（9 列 × 2 行，16×16）

### 3.1 第 0 行（y = 0..15）：底板与数字 1–8

| 行 | 列 | 像素矩形 | 色数 | 主色 | 含义 | 代码枚举 |

| 0 | 1 | (16, 0, 16, 16) | 3 | `00-00-FF` 蓝 | 数字 1 | `.digit(1)` |
| 0 | 2 | (32, 0, 16, 16) | 3 | `00-80-00` 绿 | 数字 2 | `.digit(2)` |
| 0 | 3 | (48, 0, 16, 16) | 3 | `FF-00-00` 红 | 数字 3 | `.digit(3)` |
| 0 | 4 | (64, 0, 16, 16) | 3 | `00-00-80` 深蓝 | 数字 4 | `.digit(4)` |
| 0 | 5 | (80, 0, 16, 16) | 3 | `80-00-00` 暗红 | 数字 5 | `.digit(5)` |
| 0 | 6 | (96, 0, 16, 16) | 3 | `00-80-80` 青 | 数字 6 | `.digit(6)` |
| 0 | 7 | (112, 0, 16, 16) | 3 | 纯黑 | 数字 7 | `.digit(7)` |
| 0 | 8 | (128, 0, 16, 16) | 2 | 无彩色（128 灰） | 数字 8 | `.digit(8)` |

> 数字 7 用纯黑、8 用 128 灰 —— 与 Windows 经典扫雷配色一致。
> 数字 8 的主色是灰阶，所以脚本的「主色」列显示为「无彩色」，
> 但它**不是**空白底板：底板只有 2 色（192 面 + 128 描边），
> 而数字 8 是在底板之上叠了一个 128 灰的字形（实测色数同样为 2，
> 但按字形轮廓可与底板区分 —— 底板是边框 1px，数字 8 是居中字形）。

### 4.1 LED 槽的像素结构（**红底 + 黑色七段字**）

以槽 0（数字 0）为例，13×23 逐像素：

```
KKKKKKKKKKKKK   ← 顶边框（黑）
KKRRRRRRRRRKK   ← 左边框 2px + 红底 + 右边框 2px
KRKRRRRRRRKRK
KRRKRRRRRKRRK
KRRRKKKKKRRRK   ← K = 数字笔画（黑），R = 红底，o = 未点亮的段（暗红）
...
KKKKKKKKKKKKK   ← 底边框（黑）
```

| 元素 | 颜色 | 说明 |
|---|---|---|
| 底板 | **亮红 (255,0,0)** | 每个槽**自带**红底，相邻槽拼起来即连续红底 |
| 数字笔画 | 纯黑 (0,0,0) | 七段式 |
| 未点亮的段 | 暗红 | 类似真实 LED 显示器的「熄灭段」 |
| 边框 | 纯黑 1–2px | 相邻两槽之间合计 **4px 黑**（右 2px + 左 2px） |

> ⚠️ **数字槽的右下角是黑色边框，不是红底**（实测 10 个槽全部如此），
> 所以小数点**无法**画在数字槽内部，必须独占槽位。

### 4.2 原版 HUD 的 LED 排布（反汇编 `0x403520` 确证）

| 项 | 值 |
|---|---|
| 贴图方式 | `BitBlt` 宽 `0x0D`(13) 高 `0x17`(23)、源 y = `0x20`(32)、源 x = 13 × 数字 |
| 目标 y | **4**（整数） |
| 目标 x | 依次 `16D−71` / `−58` / `−45` / `−32` / `−19`，**全部 13px 连续步进** |
| 小数点 | **图集中无对应图块**，程序也不画 |
| **位数** | **按难度自适应**：`cmp 棋盘列数, 8; jle` → 初级 3 位，其他 5 位 |
| 右边距 | 末位 x = `16D − 19`，+13 → 右边界 `16D − 6`，即**右边距 6** |

#### ⚠️ 位数不是固定的（2026-10-22 更正）

```
00403648  mov eax, [ebp + 0xC19C]   ; 棋盘列数
0040364E  cmp eax, 8
00403651  jle 0x4036B3              ; ≤ 8（初级 8×8）→ 跳过前两次贴图
00403653  ... 第 1 位（万位，x = 16D−71）  ← 只在 >8 时画
00403697  ... 第 2 位（千位，x = 16D−58）  ← 只在 >8 时画
004036D2  ... 第 3 位（百位，x = 16D−45）  ← 总是画
004036FF  ... 第 4 位（十位，x = 16D−32）  ← 总是画
00403728  ... 第 5 位（个位，x = 16D−19）  ← 总是画
```

| 难度 | 棋盘列数 | `16D` | 计时器位数 | 起始 x | 右边界 |
|---|---|---|---|---|---|
| 初级 | 8 | 128 | **3** | 83（`128−45`） | 122 |
| 中级 | 16 | 256 | **5** | 185（`256−71`） | 250 |
| 高级 | 30 | 480 | **5** | 409 | 474 |
| 超级高级 | 48 | 768 | **5** | 697 | 762 |
| 狂热 | 64 | 1024 | **5** | 953 | 1018 |

> **单位始终是十分之一秒**，5 位即 万/千/百/十/个 × 0.1 秒，最大 9999.9 秒。
> 早期实现做成「所有难度固定 3 位」，导致 123.4 秒显示成 `123`（十分之一秒位被挤掉）——
> 已按上表更正。

**雷数是固定 3 位**（`0x403B52`–`0x403B76` 只有 3 次贴图）：

| 项 | 值 |
|---|---|
| 目标 x | **6 / 19 / 32**（`push 6` 起，13px 步进） |
| 目标 y | 4 |
| 左边界 | **6** |

所以原版 HUD **左右本来就不等宽**：中级以上计时器 5 位（65px）、雷数 3 位（39px）。

> ⚠️ **「连续步进」是本节最关键的事实**：
> 原版的数码管是**一串紧挨着的槽位**，中间没有任何额外空隙。
> 本移植早前版本在两位秒与十分之一秒之间留了 4px 纯空白 + 2×2 红点，
> 红底被拦腰截断（用户实测反馈「割裂开了」）；
> 中间一版改成 4 槽（第 3 槽为纯红空槽 + 底部黑点），
> 用户仍反馈「左边这样是对的，右边你改的还是不对」。
> **最终形态：3 个连续数字槽** `[秒十位][秒个位][十分之一秒]`，
> 与左上角雷数计数器**完全同构**（同样 3 槽、39px、红底贯通）。

### 4.3 原版**没有小数点图形**（穷举确证）

逐像素穷举区域 B 的 10 个数字槽（13×23 各 299 像素）：

| 事实 | 结论 |
|---|---|
| 穷举全部 13×23 局部坐标 | **没有任何一个像素对全部 10 个数字都是纯红底** |
| 例：数字 2 的下半部有笔画、数字 5/6 的上半部有笔画 | 七段字形几乎占满整个槽 |
| 图集 11 个槽位 | 只有 0–9 + **空白槽**（纯白），**无小数点图块** |
| 反汇编 `0x403520` | 5 次 LED 贴图**全是数字图块**，**全程无单独绘制小数点的代码** |

> **三条证据一致**：原版 HUD 就是**一排纯数字的 LED 槽**，没有小数点图形，
> 也没有"纯红空槽"这种中间态。
> 计时语义为「秒.十分之一秒」：第 1–2 位是秒，第 3 位是十分之一秒位。

### 4.4 绘制坐标必须是整数

> ⚠️ 早前 LED 垂直位置用 `(height − ledH) / 2` = **4.5**（半像素），
> 矩形填充落在半像素边界被抗锯齿混合，红底呈暗红、与相邻数字槽**颜色不一致**。
> 原版的目标 y = **4**（整数），现按 `ledTopInset = 4` 定位，底边 = 32−4−23 = **5**（整数）。

对应测试：`Tests/Mine2000Tests/HUDLayoutTests.swift`
（4 项判据，核心是**渲染像素 vs 图集图块逐像素比对**）。

## 五、区域 C：笑脸（5 槽，26×26）

源 y = 55，每槽步进 26 像素。

| 槽 | 像素矩形 | 黄色像素 | 色数 | 含义 | 代码枚举 |
|---|---|---|---|---|---|
| 0 | (0, 55, 26, 26) | 160 | 5 | **正常微笑**（眼睛为两点） | `.face(.normal)` |
| 1 | (26, 55, 26, 26) | 133 | 6 | **胜利**（戴墨镜） | `.face(.win)` |
| 2 | (52, 55, 26, 26) | 158 | 5 | **踩雷失败**（X 眼，皱眉） | `.face(.lose)` |
| 3 | (78, 55, 26, 26) | 143 | 6 | **惊讶**（张嘴 O 形） | `.face(.surprise)` |
| 4 | (104, 55, 26, 26) | 160 | 4 | **备用正常脸**（无 3D 边框的平脸） | `.face(.idle)` |

**槽位与原版使用位置的对应（[已确证]）**：

| 槽 | 源 x | 原版绘制位置 | 触发条件 |
|---|---|---|---|
| 0 | `0x00` | `0x40389D` | 未开始 / 游戏中，鼠标未在棋盘上按下 |
| 1 | `0x1A` | `0x403974` | 胜利（状态 3） |
| 2 | `0x34` | `0x4039A2` | 失败（状态 4） |
| 3 | `0x4E` | `0x4038FA` | 鼠标在棋盘上按下（惊讶脸） |
| 4 | `0x68` | `0x4038C2` | 鼠标不在棋盘范围内（备用脸） |

### 5.1 表情槽的 3D 边框（「凹凸质感」的来源）

5 个表情槽**不是**同一套边框。逐像素对比左上角 3×3：

| 槽 | 左上 3×3 | 含义 |
|---|---|---|
| 0 `normal` | `#WW` / `#WW`（128 边框 + **255 白高光 2px**） | **凸起**按钮 |
| 1 `win` | 同 normal | 凸起 |
| 2 `lose` | 同 normal | 凸起 |
| 3 `surprise` | 同 normal | 凸起 |
| 4 `idle` | `###` / `###`（**纯 128，无白高光**） | **平/凹陷**按钮 |

同时右下角：`normal` 有 128 深灰阴影，`idle` 只有 192 面（无阴影）。

> 这与棋盘格的 `.coveredCell`（凸起）/ `.blankPlate`（凹陷）是**同一套设计语言**：
> 用「左上白高光 + 右下深阴影」表示凸起，两者都去掉表示按下。

### 5.2 `idle` 槽的脸**整体向右下偏移 1 像素**

| 槽 | 黄像素包围盒（槽内局部坐标） | 中心 |
|---|---|---|
| 0 `normal` | x=6..20，y=6..20 | (13.0, 13.0) |
| 1–3 | x=6..20，y=6..20 | (13.0, 13.0) |
| 4 `idle` | **x=7..21，y=7..21** | **(14.0, 14.0)** |

即：按下时不只是去掉高光，**内容本身还向右下位移 1px** —— 物理按键被按进去的位移感。
这是原版图集里做好的，实现无需额外处理（直接贴 `idle` 槽即可）。

### 5.3 按下态的原版触发条件（反汇编确证）

`0x40388E`（未开始/游戏中）/ `0x40391F`（胜利）/ `0x403978`（失败）三条分支结构一致：

```
cmp dword ptr [esi + 0x90], 1   ; 鼠标按键 == 1（未按下）？
jne <按压分支>
    → 各状态自己的表情（normal / win / lose）   ← 凸起版
<按压分支>:
    mov ecx, [esi + 0x88]       ; 鼠标格 x（-2 = 不在棋盘上）
    cmp ecx, -2
    jne → 在棋盘上：normal 用 surprise，win/lose 用自身
    （不在棋盘上 = 按在 HUD 表情按钮上）
    push 0x68 → 槽 4「idle」     ← 平脸 + 右下位移 = 凹陷
```

贴图尾部 `0x4039A4` 的 `push 3` 是 **yDest = 3**（表情垂直居中，上下各 3px）。
